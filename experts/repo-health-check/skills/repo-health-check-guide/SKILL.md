# 项目体检方法

1. **先定范围，不强行全检**：run-guide 只回答运行方式、入口、环境和最小验证；structure-and-logic 才读实现与调用链；risk-and-readiness 才评估目标相关风险；full-review 才综合交付。小问题不能被写成空泛的大报告。
2. **再定用途**：快速了解、课程评审、接手维护、发布准备和安全核验的标准不同。没有目标，不给泛化的“质量高/低”结论。
3. **运行方式与执行结果分开**：从 README、package.json、Makefile、CI 或配置中发现的命令只能算“文档/配置声明”；本轮没执行，就不能写运行成功。
4. **代码逻辑必须追真实链路**：要说“项目怎么工作”，至少读入口、关键模块和调用关系，表达为“入口 → 关键流程 → 数据/状态/外部依赖 → 输出或副作用”。只看目录树不能评价代码逻辑。
5. **建立覆盖矩阵**：每个维度写实际读到的来源、能证明什么、不能证明什么和证据状态。public-repository 公开网页浏览永远不是完整本地扫描。
6. **区分证据状态**：confirmed 是直接读取；inference 必须写前提且 severity=not-rated；evidence-gap 是未读/受限/未执行；not-applicable 说明为什么不适用。
7. **风险必须目标相关**：课程作品没做天梯、专服、重连不自动不是缺陷。先写它对用户目标的影响，再确定是否要分级。
8. **发现要可交接**：每项包含证据、影响、建议、精确路径或页面、验收标准和最小下一步验证；只查运行方式时，只保留阻塞运行或理解的必要项。
9. **结论受覆盖约束**：没有阅读源码、依赖、配置、测试或实际运行时，不能评价代码质量、可运行性、架构质量或安全性。证据不足时，明确 stop/go 条件并交付最小验证计划。

默认不扫描未授权本地目录，不登录、不克隆、不绕过访问控制，也不修改文件。

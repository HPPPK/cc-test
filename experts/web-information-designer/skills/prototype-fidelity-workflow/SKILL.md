# 原型图demo：三档保真度工作法

## 一、先确定“这张页面要让谁做什么”

每次开始先建立 `prototype-brief.md`。它不是重新写一份 PRD，而是可执行的事实表、屏幕映射与设计规范：

| 项目 | 要写清楚的内容 |
| --- | --- |
| 页面对象 | 产品落地页、产品首页、轻量工具 Demo 或信息微站 |
| 读者与动作 | 谁看；看完要下载、预约、了解、上传还是继续浏览 |
| 可用事实 | 用户确认、公开来源核验、演示占位、待确认分别列出 |
| 页面主线 | Hero → 价值 → 功能/操作 → 证据 → FAQ → Footer 的实际取舍 |
| 主 CTA | 文案、点击后只能表现的前端行为、未配置链接的诚实状态 |
| 视觉签名 | 一个来自产品语境的记忆点，而不是通用渐变/大数字模板 |
| 不可复制项 | 第三方 Logo、截图、人物、文案、图标、布局与品牌色 |

没有产品名、受众、页面目标或研究范围时，用 AskUserQuestion 补齐。不要一口气问十个问题；一次只问最会改变下一步的一个问题。

## 二、调研只做有用的部分

- 用户材料足够：不搜索，把研究状态写为“未请求公开调研”。
- 用户给链接：只核验这些链接。
- 用户要真实调研：先定义 3–6 个页面必须回答的问题，例如“用户最在意的决策条件是什么”“平台支持是否有官方依据”“竞品如何表述这个场景”。

所有外部事实必须分为：已验证事实、基于多源的分析归纳、证据缺口。搜索摘要不能当证据。访问限制不绕过，不把抓不到的样式/数据编出来。

## 三、同一个骨架派生三档保真度

先列共同的模块表和状态表，再开始写 HTML。三档中以下东西不能变化：

- 页面任务、目标用户与内容边界；
- 主导航和模块顺序；
- 主 CTA 的含义和主要操作路径；
- 功能名称与核心文案含义；
- 明确的待确认/演示占位标签。

### 低保真：`01-low-fidelity.html`

- 黑白或极少量层级色；
- 真实模块标题、信息优先级和操作路径；
- 图片用框和用途文字，不做假视觉；
- 适合讨论“漏了什么、顺序对不对、用户会先看哪里”。

### 中保真：`02-mid-fidelity.html`

- 加入同一套颜色/字号/间距 token；
- 使用已确认内容和明确标记的演示文案；
- 展示按钮、表单、展开/收起、空状态/结果状态等关键状态；
- 适合讨论“信息是否好懂、主 CTA 是否明确、模块是否过多”。

### 高保真：`03-high-fidelity.html`

- 单文件可在浏览器打开；
- 完整响应式、hover/focus、FAQ accordion、可解释动效和减少动效降级；
- 页面主体最大宽度 1200px，按 1920px 基准构图；
- 视觉呈现应来自当前产品的材料、节奏、对象和使用场景。

## 四、使用 frontend-design Skill 的方法

在高保真开始前，先写一个紧凑视觉计划：

1. **立场**：页面的语气是什么，为什么适合该产品和读者；
2. **Token**：先完成下方配色确认，列命名品牌色、中性色、语义色、标题/正文/辅助文字角色、间距与圆角策略；
3. **构图**：Hero 的表达是什么，哪些地方密、哪些地方留白；
4. **记忆点**：只选一个可解释的亮点，例如与上传前后对比、文档结构、时间线或操作反馈有关；
5. **动效**：只设计首屏、滚动揭示、hover 中真正有意义的少量节点；
6. **反模板检查**：不要因为“看起来高级”就套紫色渐变、夸张统计、所有元素居中或千篇一律卡片。

写文案时，删除以下类型的话：空泛领先、无根据效率比例、伪造用户规模、没有证据的“适用所有人”。把它换成产品实际能做的动作、适用时机和下一步。

## 四-A、配色确认与控件规范（必须落实）

配色决策按以下顺序执行，不用颜色偏好表阻塞用户，也不能擅自决定：

| 已知输入 | 正确行动 |
| --- | --- |
| 用户已给 HEX、品牌规范，或明确说“蓝白色”等配色 | 保留输入，补充相容的中性/状态 token；不重复问同一问题。不改变已给 HEX；若对比度有冲突，先调整文字/背景搭配，必要时询问是否换色。 |
| 用户明确说“配色你定” | 选适合产品的一套，记录委托依据和用途后开始制作。 |
| 只给“高级、科技、参考 Linear”、截图没有可确认色值、designIntent=choose-for-me | 这只是风格，不是配色授权；必须 AskUserQuestion。 |
| 完全没给配色 | 必须 AskUserQuestion；给 2–3 套具体配色而不是只问“喜欢什么颜色”。 |

示例问题（仅当适合当前产品时使用这些候选，不是默认模板）：
“这套原型用哪种配色？你也可以直接给品牌色。”
- 专业工具：主色 #1D4ED8、辅助 #0F766E、页面底 #F8FAFC；蓝色负责主操作，青色只提示可理解的辅助信息。
- 温暖影像：主色 #9A3412、辅助 #57534E、页面底 #FFFBF5；暖色强调操作，照片本身保留色彩空间。
- 克制工作台：主色 #18181B、辅助 #4338CA、页面底 #FAFAFA；主体黑白，靛色只给选中/强调。

选项说明还应包含正文/卡片色等必要角色的建议；实际提问须根据本轮产品替换，不能每次照搬。保留 Other/自填，用户回复后把选中 HEX 与确认依据写进 prototype-brief.md。等颜色答案时可以整理 PRD 和屏幕清单，不要先交一套未获确认的彩色成品。用户回答后同一恢复回合继续制作，不再问“现在开始吗”。

随后在简报中写一个可直接用于 CSS 自定义属性的 design-tokens 表，所有屏共用：
- 颜色：primary / secondary / accent（品牌最多三种）、canvas / surface / text / muted / border，加 success / warning / danger。语义色不能只靠颜色表达，应有图标与文字。
- 字体：中文默认 Microsoft YaHei 字体栈，正文 16px 起；分别给页面标题、区块标题、标签、说明的字号/行高/字重，不靠大标题撑版面。
- 间距与容器：4/8 基础节奏，12/16/24/32/48 的有限刻度；内容 max-width 1200px，1920 是设计基准不是固定 CSS 页面宽度。
- 控件：主/次/危险按钮，输入框、搜索、下拉、Tab、卡片、表格、Toast/弹窗；只实现 PRD 需要的，不强塞组件。
- 状态：default / hover / focus-visible / disabled / loading；输入的错误原因和改正方法放字段旁，不能只弹一句“失败”。
- 示例尺度可建议按钮高 44px、按钮圆角 8px、内容卡片 12px，确认风格后统一；卡片不是全部都需要大阴影，弹层才需要更明显层级。
- 图标固定一个开源系列、同一描边/填充风格及 16/20/24px 网格；不要混用 Emoji 冒充工具图标，图标按钮要有可访问名称。
- 明确“平面 / 轻层次 / 轻拟物”的选择理由；这是材质风格，不是“拟人化”。大渐变、高饱和、玻璃质感仅在用户确认的方向适合时使用。
- 动效建议：按钮 hover/focus 120–180ms，面板/状态切换 180–280ms；优先 opacity/transform、低幅位移。真实有进度才显示数值进度，否则用明确标记的模拟或不定进度。初始内容默认可见，不能因脚本/CDN失败或减少动效而永久 opacity:0。
- 文案落到具体对象和动作：按钮用“选择照片/预览对比/导出文件”而不是连续“立即体验”；错误提示用“未选择文件，先选一张照片”，不只说“发生错误”。没有性能测试就不写“秒级完成”，没有数据就不写“提升十倍”。

## 四-B、多屏覆盖与一致性（计数必须真实）

产品首页/控制台/工具默认 8–12 屏，至少 6 个不同任务屏与 2 个关键状态屏；落地页默认 8–10 个实质区块，不含导航/页脚。用户已明确数量优先。PRD 太小时询问缩减范围，数量目标不是新增登录、会员、支付的许可。

以下不计入屏数：同一屏低/中/高三档、手机/平板缩版、换色、空白/纯标题页、Toast 自己一屏、完全重复的卡片；加载/错误只有设计了实际内容、反馈和恢复动作才能算关键状态屏。不能重复计算同一个界面同时充当任务屏和状态屏。

在 prototype-brief.md 先建清单，每项字段固定为：
	screenId | prdRequirement（章节/原句或用户确认）| userTask | entry | exit | primaryAction | content | states | verification

每屏至少有：可理解的标题与当前上下文、主要任务区（数据/表单/结果而非空框）、一条明确主操作、返回/下一步路径、相关限制与状态提示。数据记录、术语、用户输入必须在跨屏流转中一致；演示数据统一标注。交互状态改变的是真实 DOM，不是换一张图片。

三个保真文件使用同一 screenId、任务流、字段与信息含义：
- 工具/控制台：每个画板根元素标 `data-screen-id="S01"`。默认总览模式可看到全部画板，附带目录和任务/状态分类、点击跳转；单屏操作模式可返回总览。多画板里的 id 必须唯一，用 screenId 前缀，不能出现重复 label/for 或监听器串屏。
- 落地页：真实连续网页，每块标 `data-section-id="L01"`；不把八个区块机械切成八个独立网页。
- 总览与单屏展示复用同一份 DOM 和数据，不维护两套相互漂移的静态页面；收起画板时用 hidden/inert 等避免键盘误入不可见控件。
- 所有屏必须在三档里出现，不能低保真只有首页、高保真突然多出五个功能。首页目录不能占掉正式产品的首屏主要空间。
- 若用户要独立 PNG：为每个画板提供 data-screen-id="S01" 与单屏展示入口（同一 HTML 的 ?screen=S01&export=1），用 PrototypePreview 的 screenId 参数打开，隐藏的是原型目录而不是产品导航；仅用宿主允许的本地渲染入口导出并逐张 Read。文件放 imgs/qa 并记 screenId；环境不支持时明确缺口，不改成生图。
- PNG 是扁平图片，可导入 Figma 作底图，不是可编辑 Figma 组件；HTML/CSS 才是可修改原型源码。截图、HTML 原型、生产可用代码是三种不同交付，不能混淆。

## 四-C、原创完整示例（教做法，不强套产品）

### 例 A：照片整理/修复工具的 8 屏

假设此示例 PRD 已确认：本地选图、参数设置、预览对比、导出配置、当前会话记录、处理反馈/失败重试；未接修复后端，结果只能标注演示。只有真实 PRD 也包含对应任务时才借用此映射。

| ID / 类别 | 用户任务与具体内容 | 主操作 / 状态与去向 |
| --- | --- | --- |
| S01 工作台 / 任务 | 最近任务摘要、产品限制、新建入口；空记录有解释，不塞无关指标 | 新建 → S02；查看记录 → S06 |
| S02 选图 / 任务 | 文件选择、支持格式/大小、缩略图、文件名、移除/重选 | 有效本地文件 → S03；无文件时禁用下一步，格式错误就地解释 |
| S03 设置 / 任务 | 原图预览、已确认的处理选项、输入说明、预计输出规格（未知不编） | 开始演示 → S07；返回仍保留所选文件 |
| S04 对比 / 任务 | 原图与标注“演示效果”的示例、可拖对比条、缩放、当前参数 | 查看/调整 → S03；导出配置 → S05 |
| S05 导出 / 任务 | 文件名、格式、尺寸摘要、保存说明；未接能力明确禁用 | 真实可下载内容才下载；否则显示尚未接入原因与返回 |
| S06 会话记录 / 任务 | 当前会话内文件列表、名称搜索、状态筛选、查看对应结果 | 本地列表筛选真实变化；清除需确认，不能写成云端历史 |
| S07 处理中 / 状态 | 当前文件、阶段说明、明确“模拟演示”、取消及返回 | 完成 → S04；显式演示故障 → S08；取消 → S03 |
| S08 失败与恢复 / 状态 | 保留文件和选项、具体原因、重试/更换文件、哪些数据保留 | 重试 → S07；重选 → S02；不是只有红色“失败”两字 |

主任务链：S01 → S02 → S03 → S07 → S04 → S05；S07 → S08 → 重试；S06 可回看本轮已有结果。列表若只存在内存，必须说刷新会丢失，不能伪装持久化。

控件落实示例：选图用 <input type="file"> + File 对象 + URL.createObjectURL 预览，换图时清理旧 Object URL；对比用 <input type="range"> 或等效键盘可用控件控制裁切百分比，而不是静态分割线。没有真正修复能力时，上传原图绝不能标成“AI 已修复”。

### 例 B：桌面文档工具落地页的 8 个区块

| ID | 要回答的问题 | 应展示的具体内容/构图 |
| --- | --- | --- |
| L01 Hero | 给谁、做什么、下一步？ | 具体大标题、两句说明、CTA、已确认系统；右侧可读的文档编辑器 DOM 示例，不是抽象圆球 |
| L02 价值 | 为什么用它？ | 2–3 个不同收益及对应功能，不编“节省 70%”；短段落或非等权布局 |
| L03 功能一 | 怎么开始整理内容？ | 左侧输入界面示例，右侧输入来源/限制/步骤 |
| L04 功能二 | 结果如何检查？ | 左文右界面：目录、内容、状态标签；不要复制 L03 的同一张卡片 |
| L05 场景展开 | 如何完成一个具体工作？ | 用 PRD 内另一功能或功能一的完整案例，展示输入→操作→输出，不虚构新卖点 |
| L06 使用流程 | 学习成本多大？ | 三步短流程、关键状态/可撤回点；不堆三个抽象形容词 |
| L07 可信说明 | 能信任什么，有什么限制？ | 有授权的真实证据；无证据就用透明功能示例/边界说明，不用假头像装客户 |
| L08 FAQ | 我还有哪些疑虑？ | 4–6 条具体问答、真实折叠；未知价格/平台支持写待确认 |

导航/Footer 不计数。L09 可收尾 CTA，L10 仅在 PRD 支持时增加比较或方案说明。Hero → 紧凑价值 → 交替功能 → 流程 → 可信说明 → FAQ 形成节奏，不能全部居中或全用等高卡片。用户要插画占位时用 div.placeholder 写明用途/比例，不插入别家产品截图作为本产品。

## 四-D、官方参考怎么转成设计（内置方法，不冒充本轮调研）

以下是 2026-09-11 读取官方文档文本后整理的模式，不含第三方模板代码或截图。没有颜色取样、移动端实测，不能推断这些站点的实际视觉参数。

| 官方参考 | 借鉴的抽象模式 | 在本例中落地 | 不复制/不假设 |
| --- | --- | --- | --- |
| Carbon file uploader — https://carbondesignsystem.com/components/file-uploader/usage/ | 选择入口、格式说明、文件条目、删除与上传状态分层 | S02 文件名/缩略图/移除，S07 进度，S08 可恢复错误 | 不复制 IBM 品牌或声称本原型已做服务器上传 |
| Carbon data table — https://carbondesignsystem.com/components/data-table/usage/ | 标题/工具栏/列/行操作；按数据需求选择搜索、排序、分页 | S06 的当前会话列表，空列表与搜索无结果要区分 | 不为两行数据强塞图表和分页，不照搬官方数据 |
| shadcn dashboard blocks — https://ui.shadcn.com/blocks?category=dashboard | 导航外壳、页头、工作区域分工，内容按任务分层 | S01/S06 共用外壳，移动端重排导航和工作区 | 参考的是结构，不下载整套 React 页面塞入纯 HTML |
| Tailwind Play CDN — https://tailwindcss.com/docs/installation/play-cdn | 学习原型布局模式，不依赖在线 CDN | 将所需样式内联并配合共享 CSS token | 文档把它定位为开发用途，不声称 CDN 原型已生产就绪 |

每次设计至少做 2 条适用对照：问题 → 借鉴点 → 用到哪屏 → 不照搬什么。不要只列“参考 Apple/Linear”。如果没有适用外部模式，可明确舍弃并使用上面的原创布局示例说明理由。

brief-only 使用这些已内置的方法，不联网；provided-sources 只核验用户给的链接；public-research 再真实打开 2–4 个最相关页面，不刷十几个无关首页凑来源数。外部产品事实与视觉参考分开记录，搜索摘要不等于事实。需要颜色数据时必须有浏览器计算样式/实际取样，不能从纯文本推测颜色。

图片只用用户授权材料、已核验可用的图库素材或原创占位。Unsplash 等仅作为可选候选：在已允许联网范围内核实具体图片来源、作者与用途权限，写来源记录；没实际下载不说已本地打包。不得把参考网页截图当作可自由复用的 Hero。图标优先一个可用的开源库并保留需要的许可说明；离线失败时不能留下不可理解的空按钮。

前端交互台账逐项标“真实前端行为 / 演示模拟 / 未实现”。PRD 涉及的选文件、筛选、Tab、FAQ、对比、表单校验应有真实事件与状态变化；后端部分用明确的演示开关或禁用说明，不用按钮改一句文案假装完成全流程。

## 五、受控本地截图

本地 HTML 只用宿主 PrototypePreview，不使用 Bash 截图或公开 Playwright 的 file URL。

1. 先 Write 三档 HTML；调用 PrototypePreview({"fidelity":"low"})、PrototypePreview({"fidelity":"mid"}) 各检查桌面稿。
2. 调用 PrototypePreview({"fidelity":"high"})。宿主设置真实 CSS 视口 1440×1000、1024×900、390×844，并等待三张 PNG 全部写完。
3. Read 回执里的准确 PNG 路径：imgs/qa/<runId>/ 每轮不同，不拼路径、不复用旧图。宿主记录 HTML、PNG 和 Read 审阅图哈希；HTML 或图片变化后必须重渲染、重读。
4. 多屏用 PrototypePreview({"fidelity":"high","screenId":"S01"})；HTML 提供 data-screen-id="S01" 和 ?screen=S01&export=1 展示入口，目标应实际可见。逐屏回执不替代首页回执，不支持的屏记录未观察。
5. 最终 CSS/JS 必须内联或使用已授权本地资产，不依赖外部 CDN。预览阻止所有联网请求；缺资源是 NEEDS WORK，而不是成功降级。
6. 回执中的 needs-work、裁切、横向溢出、缺资源不能被“通过”文字覆盖。修订后重新调用工具并 Read 新图。
7. 工具只提供渲染和布局测量，不证明好看、点击测试、动画测试或真机兼容；结合逐张图像审查和交互台账准确写边界。
8. 工具不可用时，记录实际错误；旧 ZIP/会话不包含 PrototypePreview 时需要升级或重新创建，禁止退回不可靠的 shell 截图命令。

不要启动本地 Web Server、上传公网或放开公开 Playwright 的私网限制。

## 六、交付前检查

- 三个 HTML 文件是否真存在、能打开，且模块和文案含义一致？
- 真实来源是否被实际打开，待确认是否仍明确标记？
- 真实评价、价格、下载地址、Logo、系统兼容性是否有用户材料；没有就没冒充？
- 截图是否真实存在、Read 已查看、证据记录没有夸大？
- 高保真是不是“可操作的页面原型”，而不是一张把三个保真度塞在一起的说明图？


## 七、与视觉质量闸门协作

在高保真阶段必须应用同包已注入的 prototype-visual-quality-gate 与 frontend-design 指南，不调用未开放的全局 Skill 工具。本 Skill 保证三档原型信息架构一致；视觉质量闸门保证高保真不是“完整但模板化”的第一版。

- 在 prototype-brief.md 中先写视觉方案，再开始高保真。
- 高保真截图需要先审图、再改 HTML、再把三个视口全部重新截图和 Read。
- 最终 prototype-evidence.md 要有 <prototype-visual-review-receipt>，而不仅是“已截图”。附屏幕数量与 PRD 覆盖、配色确认依据、逐屏内容检查、交互验证边界；正常纵向滚动不叫裁切，截图不证明点击/键盘已测。
- 未经过真实截图与 HTML 修订循环时，只能说“已生成待审原型”，不能说“视觉效果已验收”。
